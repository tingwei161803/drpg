# Configuration reference

A run is defined by two YAML files: an **agent config** (`--agent_cfg`, what the method does) and a **benchmark config** (`--bench_cfg`, which stream it runs on). `run_bench.py` merges them, copies `bench_name` and `split` into the agent config, and hands the result to the agent's constructor.

Everything under `configs/agent/` except `gt.yml` is generated by `scripts/gen_configs.py`. Edit that script and regenerate rather than editing individual files.

---

## Agent config

### Shared fields

| Field | Values | Meaning |
| --- | --- | --- |
| `agent_name` | see table below | Selects the implementation in `stream_bench/agents/__init__.py` |
| `seed` | int | Appears in the run name; the stream order itself is fixed by the benchmark config |
| `llm` | block | The agent's model |
| `policy_llm` | block | The policy generator's model (DRPG and Dynamic Cheatsheet only) |
| `rag` | block | The memory (all retrieval-based methods) |

| `agent_name` | Method |
| --- | --- |
| `rag_policy` | **DRPG** |
| `rag_policy_rag` | DRPG whose memory also stores the policy in force when each case was written |
| `dynamic_cheatsheet` | Dynamic Cheatsheet, the no-feedback ablation |
| `self_stream_icl` | Self-StreamICL |
| `mem_prompt` | MemPrompt |
| `self_refine` | Self-Refine |
| `zeroshot` | Zero-shot |
| `gt` | Oracle that replays the label; for checking the setup |

### `llm` / `policy_llm`

| Field | Meaning |
| --- | --- |
| `series` | Which client in `stream_bench/llms/` to use: `gemini_dev`, `nvidia`, `openai`, `anthropic`, `mistral`, `together`, `llama`, `groq_model`, `nebius`, `xai`, `ollama`, `hf_model`, `gemini_new` |
| `model_name` | Passed straight through to the provider (e.g. `meta/llama-3.3-70b-instruct`) |
| `temperature` | `0.0` throughout the paper |
| `max_tokens` | Output cap per call; `1024` throughout the paper |

`policy_llm` does not have to match `llm`; that is exactly the cross-generator ablation in Section 5.3.

### `rag`

| Field | Meaning |
| --- | --- |
| `embedding_model` | Encoder for both writing and querying memory. `BAAI/bge-base-en-v1.5`, CLS pooling, embeddings L2-normalized |
| `top_k` | How many past cases to retrieve. `16`; `run_bench.py` overrides it to `4` for DS-1000 and HotpotQA so the prompt still fits |
| `order` | `similar_at_bottom` (most similar example nearest the question), `similar_at_top`, or `random` |
| `rag_filename` | Where the index is persisted. `null` means "next to the run's log file", which is what you want |
| `seed` | Only affects `order: random` |

The index is `faiss.IndexFlatL2` over L2-normalized vectors. For unit vectors an L2 ranking is equivalent to a cosine ranking, so "most similar" means cosine-equivalent, not raw cosine. The embedding key is the question text alone (for DS-1000, the full prompt).

### DRPG-specific fields

| Field | Values | Meaning |
| --- | --- | --- |
| `policy_generator_mode` | `both`, `correct`, `wrong` | Which past cases the policy generator sees. `both` is the contrastive default of the paper; Appendix D shows the single-sided variants perform comparably |
| `policy_generator_fewshots_num` | `half_topk`, `two`, `one` | How many cases go to the generator. `half_topk` with mode `both` means k/2 correct + k/2 incorrect; with a single-sided mode it means k of that one kind |
| `use_previous_policy` | bool | Feed `P_{t-1}` to the generator as additional input. `false` in the paper's default design, where each policy is written from scratch (Appendix E) |
| `use_correct_fewshots` | bool | Whether the *agent's* prompt also carries retrieved correct examples. `true` makes DRPG "Self-StreamICL plus a policy"; `false` gives the agent the policy alone |
| `prompt_ver` | `original`, `LEAP` | Which policy-generator prompt template to use. `original` is the paper's |
| `mode` | `normal`, `only_correct`, `only_incorrect` | How the agent's own few-shot examples are selected. `normal` retrieves correct and incorrect cases separately; the other two retrieve once and keep only one kind |
| `enabled_cot` | bool | Switch the agent to the chain-of-thought prompt templates. `false` in the paper |
| `ewma` | `initial_alpha`, `initial_ewma` | Exponentially weighted running accuracy, written to the logs as `confidence_score`. Diagnostic only; nothing in the method reads it |
| `optimization` | bool | Legacy field. Still required by the config schema, but no code path reads it |

`dynamic_cheatsheet` uses the same policy fields, except that the agent-side few-shot switch is called `use_fewshots` and there is no `policy_generator_mode`: by construction it never sees correctness labels, which is the point of the ablation.

## Benchmark config

| Field | Meaning |
| --- | --- |
| `bench_name` | Which environment to load (`spider`, `cosql`, `bird`, `hotpotqa_distract`, `ddxplus`, `ds_1000`) |
| `split` | `test` for every benchmark in the paper |
| `feedback` | `correctness`, the binary signal DRPG consumes. The environment also supports `no_user_feedback` and `ground_truth` |
| `seed` | Shuffles the stream. `42` everywhere, so all methods see the same order |
| `db_path` | Text-to-SQL only: where `download_text2sql_data.py` put the SQLite databases |
| `setting` | HotpotQA only: `distractor` |

## Where the results go

Each step appends one JSON object to `log/<bench_name>/<split>/<run name>.jsonl`: the prompts that were sent, the raw model output, the parsed prediction, the generated policy, per-call token counts, and the running `confidence_score`. The FAISS index lives beside it as `<run name>.jsonl.db`.

`--use_wandb` additionally logs each step to Weights & Biases, into project `streambench-<bench_name>` unless `--project` says otherwise. The final metric is logged under `final/<metric>`.

Two fields in those logs are easy to misread:

- `num_inference_call` is hard-coded to `1` per step, so it is not a true call count. DRPG makes two real calls per query (policy generation, then the answer).
- The token counters *are* accurate and already include both calls, so use tokens, not calls, when comparing cost.
